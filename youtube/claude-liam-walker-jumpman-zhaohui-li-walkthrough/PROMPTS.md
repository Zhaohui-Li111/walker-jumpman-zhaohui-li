# PROMPTS — what is typed on screen, and what generated what

Two kinds of prompt appear in this reel, and they are not the same thing. This
file keeps them separate so neither is mistaken for the other.

---

## 1. B00 — the cold-open ask · **RECONSTRUCTION, not a transcript**

Shown in the composer:

> Please use Walker to convert my game design document about a one-jump 2D
> platformer — a courier automaton crossing gaps and spikes, ending in a zone
> that forks into a fast hazardous road and a slower clean climb — into a
> playable Godot project.

`runningText` on the card reads **"reconstructed ask · extended from
walker-jumpman…"**, and the beat's `role_note` states it plainly.

**Why it is a reconstruction.** This project did not begin from a blank Walker
run. It began from Nik Bear Brown's existing **walker-jumpman "First Steps"**
slice, which is recorded unmodified in the repository at commit `7f412c8`. The
ask above describes the game as it now exists, in the form a Walker prompt would
take. It is illustrative.

No fabricated build receipts, progress logs or timestamps appear anywhere in the
reel. The three RESULT lines under the card are statements about the finished
source that are each checked in [FACTCHECK.md](FACTCHECK.md):

| RESULT line | Checked by |
|---|---|
| "Character drawn in `_draw()`, collider untouched." | empty `git diff` on `tuning.gd`; unchanged collider in the diff |
| "Zone 03 forks at a raised pad." | `first_steps.json` solids; `complete-real-route-low` / `-high` both finish |
| "Finish moved 916 to 1548." | `first_steps.json` finish rect |

## 2. B10 — the Your Turn prompt (the viewer's, and it is real)

Shown in the composer, read aloud verbatim, then discussed:

> In my Godot platformer, measure the take-off window for every jump the level
> requires: sweep the jump position frame by frame with a scripted input driver
> and report, for each landing, the range of take-off positions that still land.
> Flag the narrowest one.

**Why this prompt and not a bland one.** It is the measurement this project
actually lacks. The fork-pad entry jump is the tightest input in the level, and
its usable take-off window is **calculated at roughly 46 px of run-up and has
never been measured** — stated as a limitation in CHANGE-BRIEF, TEST-REPORT §6.2
and on screen in the Verdict. The prompt turns "is this jump fair?" from an
opinion into a number, and it runs on the viewer's own level, not on this one.

What to look for in the answer: the narrowest window is where players quit. A
window under about a fifth of a second of run-up is where a jump stops reading as
a decision and starts reading as a reflex test.
